## Pictures on an idea (2026-09-28)

FR-29.5, the planner's pictures: up to four per idea, 500 KB, a banner on the card, a mosaic and a viewer in the idea
(variant C of three rendered, and *„Als Titelbild"* as the one way to reorder — both the owner's picks). ADR-081 holds
the two decisions that were real tradeoffs.

**An option rejected: the client pushes the row, the bytes follow.** It is what every other write does, and a picture
taken offline would appear at once. But every other device would pull a row whose bytes had not arrived, or never
would, and show a broken tile with no way to tell *later* from *never*; and the outbox holds JSON mutations, not
500 KB blobs. Built instead: the upload writes the row with its bytes, under the client's id so a retry is recognised.
Cost: no picture can be added offline in Server Mode, and the screen says so.

**A trap: a table's push whitelist is also what its pull returns.** The first cut listed only `position` — the one
column a push may change — and every pulled `idea_images` row came back as `{position}` alone, with no idea and no
hash, while the pushed move was refused as out of scope because `loadRow` had not read `trip_id` either. The column
set in `tableSpecs` is the row's synced shape; what a push may *touch* is the partition's write gate
(`validIdeaImage`), as `ideas.author_id` already showed.

**A premise that was wrong: the Local Mode image hash works wherever the app does.** It was a SHA-256 through
`crypto.subtle`, which exists only in a secure context — the same class as 2026-08-16's `crypto.randomUUID`. On the
owner's plain-HTTP LAN address a Local Mode photo was stored and its row never written, for item photos as much as for
the new pictures. It surfaced only because the render for the owner ran from the LAN IP rather than `localhost`. Fixed
with an FNV-1a fallback, since nothing compares a Local Mode hash with a server's; E2E-NFR-SEC-05 fails with the
fallback taken out.

## A pasted link fills the idea (2026-09-28)

FR-29.16: the server reads a pasted link's page for its title, description and picture (ADR-082). Built after #622,
on its branch.

**Who decided what.** The release check had set the precedent that an instance contacts nothing unasked, and the
recommendation was to make previews opt-in the same way. The owner chose on by default: a paste that fills nothing
until an operator reads the configuration page is a feature most instances would never have. ADR-082 records it, with
the switch back to opt-in as its revisit trigger.

**A trap the unit tests could not see: one budget for page and picture.** The first cut gave both requests 8 seconds
together. Against real sites from the owner's network, oeschinensee.ch's page came in 1.4 s and its 1.9 MB picture in
6–7 s — the preview arrived without its picture on one attempt in two. Split into 8 s for the page and 15 s for the
picture. Measured the same evening: segantini-museum.ch hyphenates its description with soft hyphens, which would split
words mid-line on a card, so the parser drops the invisible marks; myswitzerland.com answers 406 to every client that
is not a browser, header-dressed or not, and stays unreadable — the sheet then keeps what was typed.

**An option dropped mid-build: a flag in the instance config.** The client was first told by `/instance/config`
whether previews are on. It needed a new global read at boot for a control that shows only while a read is in flight;
instead the route answers `not_configured` and the device stops asking for the session.

**Then the owner waited, and saw nothing.** On the owner's iPad the sheet sat on *„Reading the link …"* — the read
did land, WebKit included, but after 6–9 s, since the page and its 2.6 MB picture came back as one answer. Split into
two reads: the words in about a second and a half, the picture after on its own, with a loading tile that already has
its ✕. A picture still coming when the idea is saved is handed over as a promise and added once it arrives; E2E-M28-09
holds the picture route back to see the words arrive first, and goes red when the save drops what is still coming.

**The owner's call on what a link may change.** Filling blanks from the page, even only blanks, put words in the idea
nobody had chosen; the owner asked for the title and description as a suggestion to confirm, and for the picture to
come without asking — in the background, after the save too, but only to an idea with no picture by then. The check
for „no picture" moved from the sheet's opening to the picture's arrival (`addLinkPicture`), since minutes can pass
between the two on a slow host. A day later the owner took the title
field out of the fill too: the site name had still been written into a blank title at once, and now it is only the
first suggestion — the one that keeps a pasted link a single tap from saving in Local Mode, where the page is never
read. And a picture fetched in the background has to show that it is coming, in the sheet and on the saved idea's
card: the planner store keeps which ideas wait for one, device state beside the synced rows. Then the owner tested it and
reported the title as still no suggestion: the suggestion stood as one card under the link, and the title field above
stayed empty, which read as nothing suggested at all. Asked with the screenshot, the owner chose the suggestion inside
each field — grey as its placeholder, *Übernehmen* in its end slot — and each field confirms its own half.

## The leftovers follow the trip (2026-09-29)

FR-7.16, from idea I-8. **A premise that was wrong:** the idea read as new work, but FR-5.10/FR-7.12 already moved
open tasks and purchases at the close and marked unpacked rows skipped. The owner believed unpacked rows were
removed; they are kept as FR-5.5's *weggelassen*, and the owner chose to leave it so. What was missing was the

**Options weighed for the mark on M6.** A shopping tag named *Von vor der Abreise* would have needed no schema,
but packing rows carry no shopping tag, and it would have overwritten an entry's own tag. A column,
`carried_over_at` on both tables, marks rows of either kind and leaves the tag alone; it cost a migration. Tasks
went the other way on the owner's call: a real task tag in the vocabulary, because M25's groups are tags already.

**Two accepted costs on that tag.** Two devices closing offline each create the tag; the name's UNIQUE index
refuses the second insert, and the foreign key then refuses every write naming that device's tag. So the tag is
written apart from the phase (a trap found in review: in one mutation, the refusal took the move to *during* down
with it). Tasks both devices knew end on the first device's tag; a task only the second knew moves, and stands
under *Ohne Tag* until somebody drags it onto the tag, which has arrived by then. The undo takes the tag off the tasks but leaves it in the vocabulary — deleting it would reach into
master data another trip may already use.

## GPX tracks on an idea (2026-10-01)

FR-29.17, ADR-085. Decided with the owner over an interactive mockup (`mockup-gpx.html`, not committed) and two rounds
of questions: several tracks per idea, hike or bike chosen by hand, *Mit Kind* by hand, pauses as the travellers' own
number, fixed child paces, the original file kept with 5 MB as the limit, at most five tracks, Leaflet, tiles on by
default with a switch, and excursions in a PR of their own.

**Who reads the file — the option rejected.** The server could have parsed the GPX on upload and written the figures
itself, which would have made them trustworthy. That is a second reader of the format beside Local Mode's (invariant
4), so the device reads it and sends what it read; the server stores the file and the row and checks only the
schema's bounds. Accepted: a member could send figures the file does not hold. The parser is a scanner over the text
rather than `DOMParser`, so `domain/track.ts` stays runnable under Node.

**A trap in replacing a file.** Replacing writes the row with a fresh server HLC. A setting that had never been
written on its own has no field clock, and the merge then takes the row's clock as its age — so an edit of the pauses
made before the replace, arriving after it, would have lost to a file it has nothing to do with. The replace pins
every setting without a clock to the row's old one first (`TestPutIdeaTrack_AnEditFromBeforeTheReplaceStillCounts_FR29_17`,
which goes red without the pinning).

**Two traps on screen.** `scrollIntoView` on the chosen chip also scrolled the sheet around it down to the chips when
an idea opened; the row now sets its own `scrollLeft`. And Chrome draws a hairline between two tiles at Leaflet's
fractional zoom; a transparent outline on each tile closes it.

**A trap in the e2e cases.** The first version waited for a tile *request* from the source it expected. It went red
once in Chromium: a tile the browser already held was drawn without a request, and none came. The cases now assert
the tile *drawn* from that source (`tilesFrom`), and every tile is answered on the device so no run reaches
swisstopo or OpenStreetMap.

## A track's route is edited on the map (2026-10-01)

FR-29.20, ADR-088. Asked for as "it should feel like the swisstopo app". Decided over an interactive mockup that used
the real public BRouter (`mockup-route-edit.html`, not committed) and four questions: BRouter asked by the device
behind a switch, both ways of saving, *Route zeichnen* in the same PR, editing locked offline. The owner's feedback
on the mockup added the direction arrows, the changed stretches in a colour of their own, and the question which
pass a tap on a doubled path means.

**The row's line cannot be edited.** The synced row carries the line thinned to 800 points and no heights, enough to
draw. Editing from it would have lost the heights of every stretch left alone, so the editor reads the track's file
back (`trackFile`, the download's path) and turns it into at most 14 handles, keeping the file's own points between
them. A track whose file cannot be read back — offline in Server Mode — cannot be edited, and says so.

**A routed handle hangs beside the path.** BRouter snaps both ends of a request to the nearest way, so a handle
dropped in a meadow was joined to a path that stopped short of it. Moving the handle onto the snapped end would have
changed the request's key and asked again. The handle is instead *drawn* where the path ends (`handlePlace`), and the
request keeps the point the finger chose.

**Blue is water.** The changed stretches were glacier blue in the first mockup; on the Landeskarte that is a stream.
Alpenrose, with heather where the track itself is alpenrose.

**Two traps in the e2e cases.** A closed `IonModal` stays in the DOM, so `toHaveCount(0)` on the editor never held;
`toBeHidden()` does. And `toBeDisabled()` reads an `ion-button` as enabled whatever its `disabled`; its
`aria-disabled` is what the cases assert, as the idea sheet's do.

## What an agent pays to read this repository (2026-10-02)

The owner asked whether token use could be cut by architecture, process or CI. Measured before changing anything:

- **The documents** — ADR-090 has the numbers and the split. The surprise was the log's index: written to be read
  *instead of* the log, it had grown to 89 KB, a quarter of what it saved.
- **A green `make ci` printed 41 KB** — npm's install report, every gate's "ok", the vitest file list, the bundle
  table. It now prints one line per target (418 bytes) and a failing target's output in full; `V=1` restores the
  stream. The verdict lives in the exit code either way, so nothing that decides anything moved.
- **A red e2e run read through `gh run view --log-failed` was 61–64 KB**, mostly the Playwright image pulled layer by
  layer and three attachment banners per failure; Playwright also prints every failure twice. `ci-failures.mjs`
  keeps 1.5–8 KB of it: the assertion, the source excerpt and the test list.
- **The trap: `gh run watch` without a terminal appends every redraw.** At its default 3-second interval a ten-minute
  run is some two hundred copies of the job table in whatever reads the output — and `make ci-remote` ended in
  exactly that call. It now waits silently and prints the verdicts once.
- **`/pr-review` told the reviewer to read `CLAUDE.md`**, which is already in every session's context — 7.5 k tokens
  read twice per review. Removed, along with the old file names.

`CLAUDE.md` went from 30 KB to 22 KB: the closed backlog list moved to `dev-docs/backlog.md`, and the long forms of
invariants 2, 3, 6, 9 and 9b, the Vitest and Playwright rules and the dev seed rule moved to `client/CLAUDE.md` and
`internal/CLAUDE.md`, which Claude Code loads when it reads a file below them. **Accepted cost:** whether Copilot CLI
loads a nested `CLAUDE.md` is not verified (`agent-tooling.md` says so); the root file keeps every invariant in short
form and names both files, so the worst case is a read on demand, not a rule unknown.

**Not in this change, on purpose:** the largest *code* reads — `PackingListPage.vue` at 130 KB, the two i18n
catalogues at ~115 KB each. Splitting them is a refactor that needs the e2e suite behind it, and riding it on a
documentation change would have put a client refactor under a review that was looking at Markdown.

## A start that stayed blank (2026-10-02)

E2E-FLOW-09 timed out twice in run 36968481090 (`e2e (chromium-5)`), each time after a `page.goto`, with a blank page
for 180 s. ADR-019 amendment 1 holds the decision; this is what the code cannot show.

**A premise that was wrong: the app's start-up awaited something.** The first reading suspected what `main.ts` waits
on — IndexedDB opening or blocked, the worker, a lock. The trace said otherwise: `<html>` never got Ionic's `ion-ce`
class, so `main.ts` never *ran*. What stalled was the module graph, on six or seven `modulepreload` chunks that came
back `net::ERR_ABORTED` under the worker and were never requested again. Nothing in the app could have caught it.

**A trap: two Chromium builds reconcile a preload under a worker differently.** The host's Playwright Chromium refuses
every preload of a worker-controlled page ("cross-world service worker resource mismatch") and fetches the 13 chunks a
second time; the CI image's build shares one request between preload and loader. The first guard counted duplicate
script fetches — red on the host, *green against the unfixed bundle in the image*, because there was nothing to
duplicate. E2E-PWA-07 now holds the condition instead (no hint in the document, at the start or after a lazy route),
red at 61 hints.

**Not reproduced locally.** 16 repeats of FLOW-09 at 8 workers on a saturated 16-core machine, a stopped worker before
the reload, and `ServiceWorkerAutoPreload` forced on all stayed green. The fix rests on the trace — every abort was a
preload — and on removing the only path those requests took. If a blank start recurs with no `modulepreload` in the
document, this diagnosis was incomplete.

## M4's page split into its parts (2026-10-02)

`PackingListPage.vue` was 3462 lines — the screen an agent opens most, read whole for almost any change to it. Split
into `views/trips/packing/`: nine composables and four components, the page left as the wiring (≈1100 lines). A pure
refactor: no `data-testid`, copy or baseline moved, and `make visual` matched all 36 baselines unchanged.

**Who decided:** the owner, asked with two questions — one PR for every cut rather than one per cut (one e2e and visual
run proves the whole), and the list body (groups → clusters → rows) as a component of its own, `PackingGroupList`,
although its interface is wide: about fourteen events, plus the row resolvers and the two long-press holds as props.

**An option rejected: composables that call each other.** The concerns share most of their state — the rows, the
closing pass, the rows still inside a removal's undo, the snackbar. Letting the menus import the actions and the
actions import the facts would have turned the file's one scope into a graph. Instead `usePackingCore` holds the shared
state and the undo-armed write helpers, is built once by the page, and every other composable takes it as an argument;
the few cross-references (the menus reach the acts and the amount editor) are passed in, not imported.

**A trap: U-10 reads the source.** `tripScreenAdoption.spec.ts` asserts that every view with a required `tripId` prop
contains `useTripScreen(props.tripId`. Moving that call into the core failed it — so the page makes the call and hands
the screen to the core, and the three components under `packing/` that take a trip id carry a written carve-out.

**A trap: state that outlives a `v-if`.** The task window's fold first moved into `TripTodosSection` with it, but the
section unmounts for the closing pass, which would have reset a fold the user set. The fold stays in the page
(`v-model:fold`), as it was.

## From an idea to the packing side (2026-10-02)

FR-29.13, the bridge: a shortlisted idea opens M27, M25 or M6 with its creator pre-filled, the result names the idea by
its own `idea_id`, and `‹` returns to the idea. The owner's four picks — the target screen rather than a sheet over the

and the route class the first one costs are ADR-078 amendment 1.

**A trap, pre-existing and only now walked into: an idea opened during the transition into M28.** Every way into an
idea from another screen — the day plan's lines, M1's *Heute* card, a notification, and now `‹` from the bridge — lands
on `/ideas?idea=`, and nothing in the suite had ever arrived that way. The new case did, and the after-case check
(ADR-012's one live page) found the page it came from still unhidden. Narrowed by probes, not guesses: the same back to
`/ideas` *without* the query left one page; the query alone made the difference. On a desktop the idea is a panel
teleported into the frame, on a phone a modal presented — either one, appearing while Ionic animated the pages, left
the leaving page standing. Built: the board opens the idea once it has entered (`onIonViewDidEnter`), for both.

**A second one, on the phone only: the sheet dismissed by the route.** Leaving the idea's sheet for another screen
closes the modal, the modal reports a dismissal, and the dismissal ran `closeSheet` — which navigated back to the board
and undid the bridge. Nothing had led from an open idea to another screen before. The dismissal now closes the idea
only while the route still has one open. The e2e suite runs at desktop width with helpers that look for the idea in the
page or the panel, so this was found by a throwaway run at 412 px, not by a case — worth knowing before trusting a
green planner run for a phone-only path.

**An accepted cost: the link is not checked for the author.** A note's excursion is its author's to change (FR-7.15);
an idea link is everybody's, since it says where a row came from rather than what somebody said. The server checks only
that the idea is of the same trip, and drops a link to one already gone.

## A setup without a homelab (2026-10-03)

The owner asked what it would take for people without Authelia to run JIT-Pack with accounts.
`deploy/multi-user-pocket-id/` answers it, with the manual's new *Easy Setup* page: Pocket ID beside JIT-Pack, both
behind the reader's Traefik in the shape of `deploy/multi-user/`. It was run end to end against the published 0.23.0
image, behind a local Traefik with a test CA and with a virtual WebAuthn authenticator in Playwright: setup, client
registration, sign-in, refresh, the admin role, the sync socket, a second household member through a login code, and
`RealProvider` against the running Pocket ID — all green. The image tag in the manual had stood at 0.4.0 for nineteen
releases; release-please now rewrites it (`extra-files`).

**Who decided:** the owner chose documentation and a stack over accounts inside JIT-Pack, so ADR-004's "no password
database or registration UI, ever" stands. An invitation link with a passkey was the alternative weighed — no password
database, but a registration UI, a second authentication path and a migration. A first version also brought Caddy for
TLS, plus a Single-User stack behind Caddy's Basic Auth; the owner kept the focus on Traefik and both were removed.

**An option rejected: Authelia, Authentik or Keycloak in the stack.** Authelia needs its users in a YAML file and its
client secret hashed by hand; Authentik and Keycloak bring a database of their own and a much larger surface. Pocket ID
is one container with SQLite and passkeys only. The cost: nobody signs in without a passkey-capable device, and the
three settings below are steps a reader has to do by hand.

**A trap: Pocket ID's first account is never verified.** `SignUpInitialAdmin` leaves `email_verified` false whatever
*Emails verified by default* says, and the admin edit form sends the stored flag back unchanged, so editing the address
there does not help either. `UI_CONFIG_DISABLED` with `EMAILS_VERIFIED` was tried and does not reach the initial setup.
What works is the account's own *My Account* form: with the setting on, a changed address is verified. The walkthrough
therefore has a placeholder address at `/setup` and the real one entered afterwards — without it JIT-Pack never grants
the admin role (FR-23.1).

**A trap: a new Pocket ID client admits nobody** until *All Users* is chosen on its Access tab, and its refresh-token
lifetime defaults to 30 days against JIT-Pack's 90. Both are steps of the walkthrough.

**A trap: the issuer has to be reachable from inside the stack by its public name.** Many home routers do not loop a
request to their own public address back in. `extra_hosts: <AUTH_HOST>:host-gateway` sends `jitpackd`'s discovery
fetch to the Traefik on the same host instead, which answers with the certificate the browser sees. With the Caddy
version this was a network alias on the proxy; Traefik lives in the reader's own compose project, where this stack
cannot give it one.

**A trap: Compose interpolates every service.** A `:?` on the client id would have refused even `up` of Pocket ID
alone, before the client can exist. The two values default to empty instead, and `jitpackd` restarts with *must be set
together* until they are filled in.

**Found, not changed:** FR-17.4's link from Single-User to an OIDC account is "always manual" and has no page in
`docs/`; the walkthrough therefore recommends starting with accounts when others will join.

## An excursion's way there and back (2026-10-03)

The owner asked for a timetable query on the excursion's screen, Switzerland first, but useful without one. A mockup
(`.claude/mockups/mockup-excursion-connections.html`, local) split it in two: this slice, the way there and back with

**Who decided:** the owner, tapping through the mockup's open points. The ways are `day_entries` rows with a role

**One thing left as #670 had it:** deleting an excursion leaves its connections on the day plan (`ON DELETE SET
NULL`). The mockup's question had said they would go with it; making that so needs either a table rebuild (migrations
are additive, ADR-067) or the packing side's delete reaching the planner's rows through a new contract, for a case
where a stray connection on the plan costs one tap to delete.
